MCP or a direct API? What the measurements and the threat model actually say.

A benchmark and security review for engineers who have not deployed MCP, written so a skeptic can check every number. The short version: latency is a non-issue, tokens are a minor issue, and the thing that decides it is how many integrations you own and how carefully you curate the tool surface.

01

Bottom line

Protocol choice is not your risk, and it is not your bottleneck. MCP adds 2 to 4 milliseconds per tool call against model turns measured in seconds, and roughly 2x the tool-schema tokens. Both are small and both are fixable. What actually breaks agents is an uncurated tool surface: when we gave a model a realistically vague request and 54 semantically overlapping tools, wrong-tool calls went from zero to hundreds and task success fell by up to 45 points, in both architectures. What actually breaks security is that MCP introduces a genuinely new injection channel (the tool description, which the model reads and your reviewers do not) plus a credential-aggregation blast radius, on top of the prompt-injection risk every tool-using agent already has.

Use a direct API integration when you own fewer than about six agent-system pairs. Use MCP above that, because the cost that dominates is not tokens, it is changing one security policy across thirty bespoke integrations instead of one. Either way, curate the tool surface per task and treat every third-party MCP server as untrusted code.

02

Decide: three questions, in this order

This looks like one decision. It is three, and "MCP or direct API" is only the second most important of them. Answer them in order. Do not skip Q1 because it sounds like an implementation detail; it had a larger measured effect than the protocol choice did.

Q1

Will one agent see more than about 10 tools?

If yes → filter the tool list per task. Not optional, and not a protocol question. This applies identically to MCP and to a direct integration.

Measured: curating the surface moved task success from 55% to 80%, tool calls per task from 23.8 to 2.0, and cost per task from $0.0134 to $0.0030. That is a larger swing than anything protocol choice produced. An agent pointed at a whole gateway works fine in a demo and degrades badly on realistically vague requests.

Q2

How many (agent × system) pairs will you own in 12 months?

1 to 5 → direct API. 6 or more → MCP. A vendor already ships an MCP server for that system → MCP, at any count.

Direct integration is an A × S problem; MCP is A + S plus a gateway. Below ~6 pairs the gateway is overhead you do not need. Above it, the cost that compounds is not tokens, it is applying one policy change across N×M integrations. If a vendor ships the server your build cost for that system is roughly zero, which beats the arithmetic outright.

Q3

Only if you chose MCP: is the loop chatty and the server remote?

More than ~10 sequential calls per task over a WAN → co-locate the server (sidecar or stdio). Otherwise a central gateway is fine.

Measured: a remote gateway costs 2.0× the one-way RTT per tool call, because a streamable-HTTP call makes two client-facing trips. At a 30 ms hop that is 60 ms per call. Under ~10 calls it stays inside the noise of a model turn.

Note what is happening. With one system, MCP has more integrations to build at every single row: A + 1 always exceeds A. On integration count alone MCP never wins here. It flips at eight agents anyway, and the entire reason is the governance column: applying one policy change across eight bespoke integrations costs $13,440 a year against a flat $1,680 at a single chokepoint.

The practical rule. Do not build an MCP server to connect your own agent to your own app. Below roughly eight consuming agents it is strictly more work for a new attack surface and 2.1× the schema tokens. Above that, what you actually need is a chokepoint, and MCP is only one way to get one; an API gateway or a thin internal tool-broker gets you the same governance on technology you have already accredited.

The exception is distribution, not integration. If you are publishing a capability to consumers you do not control, or your users live in an MCP-native host that cannot call your REST API at all, then MCP is a reach decision and the integration arithmetic above does not apply. You are not paying the A side; your consumers are.

Be honest about what drives this. At 5×6 the measured token term is $1,991 of a $40,471 MCP bill, about 4.9%. The benchmark's headline quantity barely matters at scale; the assumed labour rates decide it. If your teams build integrations far faster than 24 hours, or you rarely change policy, the threshold moves up. Run analysis/crossover.py with your own numbers.

03

What MCP actually is, if you have never used it

An LLM agent calls tools. Something has to tell the model what tools exist (a name, a description, a JSON Schema for the arguments) and something has to execute the call. The two architectures differ in where those two things live.

Direct API. The tool schemas are source code in your agent. The agent makes one HTTP call to the backend. There is no protocol, no handshake, and no tool discovery. You write and maintain this once per (agent, backend) pair.

MCP. A separate MCP server advertises the tools over JSON-RPC. Your agent connects, calls initialize, asks for tools/list, and then issues tools/call. The server forwards to the backend. Write the server once and any MCP-speaking agent can use it.

A distinction that trips people up. "Just run MCP locally as tools" is not the same as a direct API integration. Running the MCP server as a local subprocess still speaks the full protocol and still loads the server's tool descriptions. In our measurements the local and remote MCP arms carried the identical 2,309-token schema. Moving MCP closer to your agent fixes latency, which was never the problem. It does nothing about tokens, which were.

The structural argument for MCP is arithmetic. With A agents and S systems, direct integration is an A × S problem and MCP is an A + S problem. That is the whole debate, and it is why the answer depends on your scale rather than on the protocol.

Latency: real, small, and mostly a client-configuration story

Measured — no LLM in the loop, backend latency fixed at 40 ms, jitter 0

Protocol overhead is isolated by subtracting the backend's self-reported service time from wall clock, so what remains is framing, serialization and transport. Warmup discarded, bootstrap 95% CI on the median.

Against a model turn of 800 to 5,000 ms, single-digit milliseconds is noise. The latency objection to MCP does not survive measurement.

But a remote gateway costs two round trips, not one

Sweeping an injected one-way delay, with the gateway's own upstream call deliberately exempted so the only thing varying is agent-to-gateway distance:

Injected delayOverhead p50Above baselineMultiplier
0 ms6.94 msbaseline—
10 ms26.15 ms+19.20 ms1.92×

Dead flat at 2.0×, because a streamable-HTTP tools/call makes two client-facing trips. Take your measured RTT to a central gateway and double it. At a plausible 30 ms cross-region hop that is 60 ms per call, so a task making eight calls pays half a second in network alone. This is the one place the "deploy MCP closer to your agent" instinct is straightforwardly correct.

The number that dwarfs everything else is a client bug

A client that re-runs initialize and tools/list on every request measured 1,015 ms per call, against 3.35 ms pooled. That is roughly 300×, and it is a connection-pooling defect, not a property of MCP. If someone tells you MCP was slow in production, check this first.

caveat This is a single run at n=40, the smallest sample in the set, and the harness records the handshake once rather than per call, so it understates the true naive cost by about 89 ms. The 230× to 317× spread depends on which pooled baseline you compare against. Treat "roughly two to three orders of magnitude" as the finding, not the precise ratio.

Tokens and quality: curation beats protocol

Measured — deepseek-chat, 5 graded tasks, deterministic state-based checkers

Identical capability over an identical backend. The MCP server costs about twice the schema tokens, purely because a general-purpose server writes descriptions for an unknown consumer while a hand-written integration is tuned for one caller.

ArmToolsSchema tokensUtilisation
direct111,08024.6%
mcp_sidecar112,30925.6%
mcp_filtered41,24687.8%

Utilisation is the share of loaded schema weight belonging to tools the agent actually called. The complement is context you pay for on every turn and never use.

The experiment that changes the recommendation

Our first sweeps found that adding up to 150 irrelevant tools cost money and nothing else: success stayed at 100%, and the model never once called a distractor. That result was an artifact. The task prompts named their own domain ("every support ticket that is open and priority P1"), so the model could route on keyword overlap without ever discriminating between similar tools.

Rewriting the same tasks the way a person actually asks ("whoever is carrying the pager needs to own everything urgent that hasn't been picked up") while keeping the checker identical produces a completely different picture:

Request phrasingExtra tools loaded nSuccessWrong-tool calls
Explicit108 near-miss10100%0
Explicit54 near-miss20100%0
Vaguenone1080%3
Vague54 cross-domain1060%0 distractors
Vague54 near-miss3060%125

It is an interaction, and neither ingredient alone does it. Similar tools with an explicit request are completely harmless: 100% success and zero wrong calls even at 108 extra tools. A vague request with unrelated tools hurts success but never causes a wrong tool call, so that failure is comprehension, not selection. Only vague requests and semantically overlapping tools produce the wrong-tool explosion. Both are the normal enterprise condition.

The failure mode is diagnostic. The agent calls list_accounts, then list_accounts_v2, v3, v4, v5, shotgunning every near-duplicate because nothing tells it which is authoritative. That is precisely what a gateway fronting six systems that all model "accounts" produces.

Two things worth sitting with. First, direct came out worst. Its terse hand-written descriptions are cheaper per token but more confusable against a crowded surface, where the MCP server's verbosity buys discrimination. The 2.1× token premium is not pure waste; part of it is paying for legibility.

Second, and importantly for honesty: the filtered arm's 80% is exactly the vague-phrasing baseline with no distractors at all. Filtering does not beat the problem, it removes it and returns you to the ceiling set by request ambiguity. That remaining 20% is a comprehension limit no amount of tool curation will fix.

measurement caveat The harness deduplicates the per-trial tool list, so counts of distinct distractor tools touched are exact but counts of distractor invocations are bounded, not precise. The wrong-tool-call totals quoted above are exact (incremented per call). At n=10 to 30, success differences under about 25 points sit inside the Wilson interval. The wrong-tool differences, 0 versus 125 versus 377, do not.

Caching helps less than people assume

DeepSeek's automatic prefix cache hit 92 to 96% across the sweep and per-task cost still tripled as tools grew. A high hit rate cuts the marginal rate; it does nothing about sending six times the tokens.

There is also a trap worth knowing: prompt caching has a minimum cacheable prefix, and it is not monotonic across model generations. A tight hand-written tool block can be below the floor and therefore never cacheable, while the bloated gateway block is the only one large enough to qualify.

ModelInput $/MtokMin cacheable prefix
claude-opus-5$5.00512
claude-sonnet-5$3.001,024
claude-haiku-4-5$1.004,096

The cheapest model has the highest floor: 8× the threshold at 1/5 the price. So "route to the cheap model" and "cache the tool block" can be mutually exclusive at small block sizes. The failure is silent, with no error and a cache-creation count that simply stays zero.

06

Security: what is genuinely new, and what is not

The most common analytical error in this space is attributing generic LLM-agent risk to MCP. Below, risks are separated by what actually changes when you adopt MCP. Getting this wrong in either direction is expensive: it either paralyses an MCP rollout over risks you already carry, or waves through the ones that are genuinely new.

Risks that are genuinely new or materially worse with MCP

RiskMechanismMitigationSeverity
Tool poisoning Malicious instructions embedded in a tool's description. The model reads it as authoritative context; a human reviewing a tool list in a UI may never see it. Demonstrated publicly by Invariant Labs, April 2025, exfiltrating private repo contents with no user interaction. Pin and diff tool definitions; render full descriptions in approval UI; treat descriptions as untrusted input. critical
Rug pull A server changes its tool definitions after the user approved them. MCP has no continuous re-verification once trust is extended. Hash tool definitions at approval; alert and re-consent on change; version-pin servers. critical
Cross-server shadowing One malicious server's descriptions influence how the agent uses a different, trusted server's tools. Do not co-load servers of differing trust levels in one context; isolate per trust boundary. critical
Credential aggregation A gateway holding tokens for many systems turns one compromise into all of them. Direct integrations fail independently. Per-user not per-service tokens; audience-bind tokens; downscope; segment gateways by trust domain. critical
Confused deputy MCP proxy with a static upstream client ID plus dynamic client registration plus a consent cookie lets an attacker obtain an auth code without consent. Described normatively in the spec. Spec MUST: per-client consent stored server-side, exact redirect-URI matching, single-use state set only after consent. critical
Token passthrough Server accepts a token not issued for it and forwards it downstream, bypassing rate limits and destroying the audit trail. Spec MUST NOT. Validate the audience claim; use RFC 8693 token exchange. critical
Local server compromise Local MCP servers execute with full user privileges. A malicious startup command in a config, or a poisoned package, is arbitrary code execution. Show the exact command before execution; sandbox; prefer stdio over an open local HTTP port. critical
SSRF via OAuth discovery A malicious server returns metadata URLs pointing at 169.254.169.254 or internal services; the client fetches them, leaking cloud credentials. Enforce HTTPS; block private and link-local ranges; validate redirect targets; use an egress proxy. high
Dangerous auth URL schemes A server supplies a javascript: authorization URL; a client that opens it via shell or window.open gets XSS, and via a proxy architecture, RCE. Allowlist https: only; never open URLs through a shell. high
State handle hijacking MCP is stateless; servers mint handles passed back as ordinary tool arguments. Possession is not authentication. Bind handles server-side to the authenticated user; non-deterministic IDs; expiry. high

Risks that are worse with direct API integration

RiskMechanismSeverity
Credential sprawl A × S integrations means credentials in many codebases. Rotation and revocation scale with the product, and one forgotten integration keeps a live token. high
Authorization drift Each integration implements its own scoping. Least privilege decays independently in each one, and nothing detects the divergence. high
Audit fragmentation No chokepoint for tool-invocation logging. Incident reconstruction means correlating across N services with N log formats. high
Policy change cost Adding PII redaction or an egress allowlist means touching every integration. In the cost model this is the single largest term at scale. medium

Risks common to both, which MCP is often unfairly blamed for

Indirect prompt injection is an agent problem, not an MCP problem. If a tool returns attacker-controlled text (a ticket body, an email, a web page), that text enters the model's context and is indistinguishable from instructions. This is identical in both architectures. Adopting or avoiding MCP does not change it at all.

The useful framing here is Simon Willison's lethal trifecta (June 2025): risk becomes acute when an agent simultaneously has

  1. access to private data,
  2. exposure to untrusted content, and
  3. the ability to communicate externally.

Remove any one leg and exfiltration becomes much harder. This is an architectural test you can apply to a design review in about two minutes, and it is protocol-agnostic. Over-broad tool scope and lack of human-in-the-loop on irreversible actions are likewise shared failures.

Pre-production checklist

Judgement — derived from the spec's normative requirements and the incident record

Must be true before production

  • Curate the tool surface per task. Never point an agent at an entire gateway because it happens to work. Measured: this dominated every other variable.
  • Apply the lethal-trifecta test. If an agent has private data, untrusted input and an egress path simultaneously, remove one leg or accept that exfiltration is achievable.
  • Validate token audience. Never accept a token not issued for your server, and never forward it downstream. This is a spec MUST NOT.
  • Per-client consent before third-party auth, with exact redirect-URI matching and single-use state set only after approval.
  • Human-in-the-loop on irreversible actions. Gate by reversibility and blast radius, not by how "important" the tool sounds.
  • No secrets in model context. Inject at the egress boundary so the sandbox and transcript never see the real value.
  • Pin third-party server versions and review the diff. Treat every server as code running with your credentials, because it is.

Hardening

  • Hash tool definitions at approval and alert on change (rug-pull detection).
  • Render full, untruncated tool descriptions in any approval UI (tool-poisoning detection).
  • Egress allowlist per credential, so a stolen token cannot be sent anywhere.
  • Block private and link-local IP ranges on any URL the client fetches (SSRF).
  • Allowlist https: for auth URLs; never open a URL through a shell.
  • Bind session and state handles server-side to the authenticated user.
  • Log every tool call with caller identity, arguments and outcome, at the gateway.
  • Sandbox local MCP servers; prefer stdio over an open localhost HTTP port.
  • Do not co-load servers of different trust levels into one agent context.
  • Scope minimisation: start with read-only, elevate on demand rather than granting a full catalog up front.
09

What this evidence does not establish

Stated plainly, because a brief that only lists its confirmations is a marketing asset.

  • One model. Every agentic result is deepseek-chat. Tool-selection behaviour is model-specific and will not transfer across families. Rerun the sweep on what you deploy.
  • Small samples. n=10 to 30 per cell. Success differences under roughly 25 points are inside the Wilson interval. The wrong-tool differences are far larger than that and are safe to rely on.
  • Five tasks, one synthetic domain. No pagination, no partial failures, no long-running jobs, no streaming payloads.
  • Lab network. No mTLS, no service mesh, no cross-AZ hop. The netem multiplier (2.0×) should transfer; the absolute milliseconds should not.
  • Cost inputs are assumed. Only the token delta is measured. Build hours, maintenance hours and policy-change frequency are defaults.
  • Security content is a literature and spec review, not a penetration test. Nothing here was exploited in a lab. Verify each CVE against its primary source before citing it.
  • Blast radius is unmeasured and cuts against MCP. A shared gateway is a shared failure domain; the benchmark says nothing about it.
